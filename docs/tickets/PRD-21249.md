## Product design

### Goals / Non-goals

**Goals (v1, MVP):**
- An Agent on the MSPbots platform can, through this MCP server, for a WatchGuard Cloud MSP account reachable with the caller's credentials:
  - look up and list managed (child) accounts, create a new managed account, update one, remove one (**Accounts**);
  - submit a device/license activation request, list recent activations, and check the status of a submitted activation batch (**Activations**);
  - create, update, remove a WatchGuard operator, list operators for an account, and poll the status of an async operator change (**Operator Management**);
  - read device/license allocation inventory (summary, allocations, licenses owned, assets assigned) for an account (**read-only Allocations**, see Non-goals).
- The connector follows the existing MSPbots connector contract: Streamable HTTP, stateless, credentials only from request headers, structured errors — so it plugs into the same gateway, dashboard, and per-role tool allowlist every other connector already uses (`wiki: ProductDocs/_connector-fields.md`).
- Works for an MSP acting on its own account (no `accountId` argument needed) and for an MSP acting on a managed customer account it has been delegated access to (pass that account's id).

**Non-goals (v1):**
- **Allocation mutation** (`POST/DELETE /v2/{accountId}/assets`, both `PUT` update-allocation endpoints) is explicitly **out of scope for v1**. The ticket's three stated capabilities are accounts, activation, and operator access; allocation changes affect what a managed account is billed/entitled for and were not asked for. See "Decisions made by DEV01" in the tech design. Read-only allocation/inventory queries remain in scope because "activate devices and licenses" implies being able to see what is allocated.
- No changes to the Agent platform UI. The credential form for this connector is generated by the platform from the `credential_fields` supplied at vendor registration (same mechanism as every other "variant 1 / credential-based" connector in `wiki: ProductDocs/_connector-fields.md`); no platform code change is implied by this ticket.
- No OAuth authorization-code / "Connect on vendor's page" flow. WatchGuard's own API uses client-credentials with an Access ID + Password the customer already has; the connector exchanges that for a token itself per request, like several existing connectors with a Client ID/Secret pair (e.g. HaloPSA, ConnectWise Manage) in `wiki: ProductDocs/_connector-fields.md`.
- No changes to `mcp-service-gateway` or any control-plane repo — the design fits entirely inside a vendor MCP server behind the existing gateway contract.

### Acceptance criteria

- **AC1** — Given valid credentials (Access Id, Password, Api Key) in request headers, When an Agent calls `initialize` then `tools/list`, Then the server returns the full `watchguard_*` tool catalog (accounts, activations, operators, and read-only allocations tools) with names, descriptions and schemas, and a subsequent `tools/call` for a read-only tool (e.g. `watchguard_get_account`) succeeds.
- **AC2** — Given the `X-WatchGuard-Account-Id` header is **not** supplied, When any `watchguard_*` tool is called, Then it operates on the account that owns the supplied credentials (no account id required for the common case) — it must never fall back to some other account's data.
- **AC3** — Given any one of the required credential headers (Access Id / Password / Api Key) is missing, When any `watchguard_*` tool is called, Then the server returns HTTP 401 with a body listing which header(s) are required, and does not fall back to an environment variable or any other credential source.
- **AC4** — Given `X-WatchGuard-Account-Id` **is** supplied for a managed (child) account the caller's MSP account has been delegated access to, When a tool is called, Then the server first resolves that account's `audience` (Authorization API) and requests an access token scoped to it before calling the underlying WatchGuard endpoint, so the call acts on the managed account, not the MSP's own top-level account.
- **AC5** — Given a vendor API call fails, When the failure is 404 / 429 / 5xx / an unmapped error, Then the tool returns the structured envelope `{"error":{"code","message","retryable"}}` with `code` one of `not_found` / `rate_limited` / `upstream_error` (matching the failure), rather than raising an unhandled exception or a bare HTTP status; 429 and 5xx responses are retried with backoff honoring `Retry-After` before the error is ever returned to the caller.
- **AC6** — Given `watchguard_delete_account` or `watchguard_delete_operator` is called, When invoked, Then it requires an explicit, single resource identifier (an `accountId`, or a `username` + `accountId` pair) — no wildcard or "all accounts/operators" form exists — and the tool is marked `destructiveHint: true`.
- **AC7** — Given an operator create/update/delete call returns a `transaction_id` (WatchGuard's documented async pattern for these operations), When the tool returns, Then its result includes that `transaction_id`, and `watchguard_get_operator_transaction_status` can be called with it to retrieve the final outcome.
- **AC8 (multi-tenant isolation)** — Given two different MSPbots tenants both have this connector configured with different WatchGuard credentials, When their Agents call `watchguard_*` tools concurrently, Then each call only ever uses the credentials carried on its own request (request-scoped `ContextVar`) — no token, account id, or response data from one request is readable by, or cached for, a different request. There is no module-level or global cache of tokens or account data.
- **AC9 (no test account is not a blocker)** — Given no real WatchGuard Cloud account is available for end-to-end testing (per `legs/dev.md`/`mcp-track.md`, this is explicitly not a blocker for vendor MCP tickets), Then the self-test instead verifies, with placeholder credential headers: `tools/list` returns > 0 tools with the expected names/params, missing-header requests return 401, `/health` returns 200, and vendor-call paths are covered with mocked HTTP responses (success, 401, 404, 429, 5xx) — see Test strategy.

## Tech design

### Conclusion

Build a new Python/FastMCP service (SOP "Main line A", clean-room against WatchGuard's public API docs). One HTTP layer wraps WatchGuard's OAuth client-credentials exchange plus the five API areas; a thin tool layer maps each vendor capability group to a small set of Agent-facing tools (17 total, under the 20-tool cap), consolidating read/list/CRUD per resource rather than mirroring every vendor endpoint 1:1. Credentials and tokens live only in a request-scoped `ContextVar` — never cached across requests — because token caching would reintroduce the cross-tenant shared-state risk the platform's isolation contract forbids; the cost is one extra HTTP round trip (token exchange) per tool call, which is acceptable because the vendor's rate limits are per-account, not shared across the connector.

### Where the current implementation lives

None — `MSPbotsAIFramework/watchguard-mcp@e8caef0` is a 2-line README with no code (see "Current state"). There is no MSPbots connector for WatchGuard Cloud to extend or follow; the closest sibling pattern is the general SOP in `~/.claude/skills/vendor-mcp-development/SKILL.md` §A3/A4, which this design follows directly.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A — per-request token exchange, no caching | Every tool call does `POST /oauth/token` (and `/audiences` if a managed account id is given) before the real API call | Fully stateless, no cross-tenant leak surface, trivially correct under the platform's "request-level isolation" rule | +1 (or +2) HTTP round trip per tool call (~200-500ms) | **Chosen** |
| B — server-side token cache keyed by credential hash, TTL ≈ 55 min | Cache the bearer token in memory across requests for the same credentials | Saves the extra round trip on repeat calls | Reintroduces a module-level store keyed by a value derived from a secret; a cache-key collision or TTL bug leaks one tenant's token into another's request; explicitly the shape of shared state SOP §3.3/§3.4 bans ("never use a global variable or module-level singleton to store credentials ... never cache a derived token across requests") | Rejected |
| C — 1:1 tool per vendor endpoint (≈20+ tools incl. Allocations mutation, Authorization `/audiences` as its own tool) | Mirror every documented endpoint as a tool | Nothing is hidden; simplest mapping | Blows past the practical tool-count/clarity budget, exposes an auth-plumbing endpoint (`/audiences`) as a user-facing "tool" with no business meaning, and hands the agent write access to license allocation nobody asked for | Rejected (see Non-goals) |

### Data & API contract

**Credential headers** (all per-request, never persisted, never logged; `X-WatchGuard-Account-Id` is the only optional one):

| Header | Required | Notes |
|---|---|---|
| `X-WatchGuard-Access-Id` | yes | WatchGuard Cloud Access ID (read-write or read-only), from WatchGuard Cloud → Manage Access page |
| `X-WatchGuard-Password` | yes (masked) | Paired with Access Id for the Basic-auth client-credentials exchange |
| `X-WatchGuard-Api-Key` | yes (masked) | `WatchGuard-API-Key`, from the same Manage Access page; sent on every vendor call per WatchGuard's docs |
| `X-WatchGuard-Account-Id` | no | Target managed account id, format `WGC-1-xxxxxx`; omit to act on the account owned by the credentials themselves (AC2) |

**Tool catalog** (17 tools; `readOnlyHint`/`destructiveHint`/`idempotentHint` set per SOP §A4; all list tools take `limit` ≤ 50 default / ≤ 200 hard cap and return `has_more`):

| Tool | Vendor call | Hints |
|---|---|---|
| `watchguard_get_account` | `GET /v2/accounts/{accountId}` | read-only |
| `watchguard_list_child_accounts` | `GET /v2/accounts/{accountId}/children` | read-only |
| `watchguard_create_account` | `POST /v2/accounts/{accountId}` | not idempotent |
| `watchguard_update_account` | `PATCH /v2/accounts/{accountId}` | idempotent |
| `watchguard_delete_account` | `DELETE /v2/accounts/{accountId}` | destructive |

**Error envelope** (returned as the tool's string result, never an uncaught exception):

```json
{"error": {"code": "not_found", "message": "Account WGC-1-000000 was not found", "retryable": false}}
```

`code` ∈ `not_configured | unauthorized | not_found | invalid_argument | rate_limited | upstream_error`; `retryable` is `true` only for `rate_limited` and `upstream_error`.

**Backward compatibility**: not applicable — first version of a new connector, no existing callers.

### Key flow / sequence

```
Agent -> Gateway -> watchguard-mcp: tools/call watchguard_get_account {accountId?}
  middleware: read X-WatchGuard-* headers -> missing required? -> 401 (AC3)
              set ContextVar(credentials)
  tool: client.get_access_token()
          POST https://api.usa.cloud.watchguard.com/oauth/token
            Authorization: Basic base64(access_id:password)
            body: grant_type=client_credentials&scope=api-access[&audience=<resolved>]
          if X-WatchGuard-Account-Id present and no audience yet:
            POST /v1/audiences {accountId} -> audience  (AC4)
            (retry the token request with that audience)
  tool: GET /v2/accounts/{accountId or credential-owner's account}
          Authorization: Bearer <token>
          WatchGuard-API-Key: <api_key>
  on 429/5xx: backoff + retry, honor Retry-After, budget < 120s total (AC5)
  tool: map response -> compact JSON result (no indent=2, ensure_ascii=False)
  finally: ContextVar.reset()  (AC8)
```

### Non-functional

- **Idempotency & concurrency**: service is fully stateless; every request authenticates independently via its own `ContextVar`. Create/activate calls are explicitly **not** idempotent (resubmitting creates a duplicate — this is the vendor's contract, not something this connector can paper over); update/delete calls are idempotent by vendor id.
- **Performance**: every tool call costs one token exchange (+ one `/audiences` call when a managed account id is given) plus the real API call — accepted trade-off (see Option B rejection). List tools cap at `limit` ≤ 200, default ≤ 50, to keep tool-call token cost small (SOP §A4).
- **Security**: credentials exist only as header values on the incoming request and as the request-scoped `ContextVar`; never written to logs, disk, or environment. The error envelope's `message` never includes the Access Id, Password, or Api Key, even when the vendor's own error body echoes a header (scrubbed before logging/returning).
- **Multi-tenant isolation**: the only state the service holds is the `ContextVar`, set and reset per request (AC8); no global or module-level cache of tokens, accounts, or vendor responses.
- **Observability**: structured logs per call include ticket-irrelevant fields only — tool name, vendor HTTP status, retry count, latency — never header values or token contents.

### Rollout & rollback

- This is a brand-new connector with no existing tenants, so there is no feature flag or gradual rollout — the first version is pushed straight to `main` (SOP A2, no dev-lock needed for the very first commit) and registered via `/api/vendor-register`, which performs the first INT deployment as part of registration.
- **Rollback risk to flag, not block**: WatchGuard vendor registration is a one-time "new name" operation (`/api/vendor-register` rejects a name that already exists). If this version needs to be pulled after registration, there is no documented de-registration endpoint — rollback would mean shipping a fixed version under the same registered name via the normal `/api/deploy-int`, not re-registering. This only matters post-registration and does not block this ticket.

### Decisions made by DEV01

(No one is available to ask for a brand-new connector's scope calls; each is a reversible, non-blocking choice — see `[DESIGN DECISIONS]` comment for the ClickUp-facing copy.)

1. **v1 excludes Allocations API mutation** (`POST/DELETE /v2/{accountId}/assets`, both `PUT` update-allocation endpoints). Why: the ticket's three stated capabilities map to Accounts, Activations, and Operators; Allocations overlaps with Activations and its mutating endpoints change what a managed account is billed/entitled for, which nobody asked for. Alternative not chosen: implement full Allocations CRUD — rejected to avoid unrequested billing-affecting writes in a first version; read-only allocation/inventory tools remain in scope.
2. **No server-side token caching across requests** — every tool call fetches a fresh access token. Why: required by the platform's request-isolation contract (no module-level credential/token cache); the alternative (TTL cache keyed by credential hash) reintroduces exactly the shared-mutable-state risk that contract exists to prevent, for a latency win that is not worth it at this request volume. Alternative not chosen: cache tokens for ~55 minutes — rejected.
3. **Managed/child-account access is exposed as a single `X-WatchGuard-Account-Id` header**, resolved server-side into the vendor's `audience` concept, rather than asking the caller to supply the `audience` value directly. Why: keeps the tool/header contract simple and consistent with how other MSP connectors expose a single "target account" field; `audience` is a vendor auth-plumbing detail that shouldn't leak into the tool contract. Alternative not chosen: expose `X-WatchGuard-Audience` directly — rejected.
4. **Single global API base URL assumed** (`https://api.usa.cloud.watchguard.com`), no region selector. Why: WatchGuard's fetched documentation names only this host. Alternative not chosen: add a region header like IT Glue/Auvik's connectors — rejected for v1 since there is no second host to point it at; trivially addable later if WatchGuard confirms one exists.
5. **`watchguard_delete_operator` calls the vendor's `POST /v1/DeleteOperators`** rather than normalizing the connector's internal call shape to a `DELETE` verb. Why: keep the connector's internal implementation a faithful 1:1 mapping to the vendor's actual contract instead of inventing a REST shape WatchGuard itself doesn't use; the MCP tool name/semantics (`destructiveHint: true`) are what the Agent sees, so this has no user-facing effect. Alternative not chosen: wrap it to look like a DELETE — rejected as unnecessary indirection.
